### 止まった点・失敗した点（**必須。1件以上**）
- **何が起きたか**: 実装パッチ（1 スクリプト・順次置換）が `cli.py` の facts 出力行で外れて途中停止し、前半（summarize / overview / facts）だけ当たった半端な状態になった
- **原因**: 出力行の f-string が `report.skipped_no_date` でなく `d['skipped_no_date']`（dict 経由）で、regex を推測で書いた。「1 回一致でなければ止める」は正しく働いたが、**適用が順次**なので途中停止＝部分適用になる
- **次にどうするか**: 置換スクリプトは**先に全置換対象の存在を検査（dry-run）→ 全部揃ってから適用**の 2 段にする。外れた分は残りだけのスクリプトを切り出して当てた
- **何が起きたか（2 件目）**: ruff E501 が日本語 docstring で 5 件。全角は幅 2 で数えられる（88 桁＝日本語なら約 44 字）
- **次にどうするか**: 日本語のコメント・docstring は 40 字で折る
- **何が起きたか（3 件目）**: ゲートの exit をパイプ越しに `$?` で見て 0 と読んだ（実際は pytest 失敗で 1）。**監視役の検証で、監視役の出力をパイプに通した**
- **次にどうするか**: exit code を証拠にする時はパイプ無し（`cmd > log 2>&1; echo $?`）か `${PIPESTATUS[0]}`。故障注入の結果は「0 以外が正」と期待値を先に書く

### 学んだこと
**技術的な学び**:
- 具体: `summary.source_hash` は 0009 から保存していたが、どこも読んでいなかった（陳腐化した要約が overview に黙って出る）
  - 抽象: **ハッシュを保存するだけでは何も検知しない**。検知は「生成側と同じ関数で再計算して比較」まで実装して初めて成立する。計算関数は生成側と検証側で**共有**する（別実装だと片方の変更で検知が壊れる）
- 具体: `recorded_at` の代用に `ingested_at`（取り込み日＝2026-09-29）を使うと、memory の古い記録 6 件が「今日記録した」ことになる
  - 抽象: バイテンポラルの記録時間は「DB が知った時刻」でなく「正本に書かれた時刻」で定義しているなら、代用も正本側の時刻（valid_from）から取る
- 具体: count bench は「3 回同じ値」だけを見ていたので、Q12 が誤ったビュー（v_unverified の補集合）のまま以前から「4/4 stable」だった（受入検証の指摘）
  - 抽象: **安定性の判定器は正しさを測らない**。判定器には期待値との照合を必ず持たせ、期待が無い問いは「不明」にする（正解扱いにしない＝前単位 D5 と同型）
- 具体: FD の制約リストで 1 行（識別子）を直した時、隣の行（「閉じて挿入・削除しない」）が実装と逆のまま残った（R6）
  - 抽象: 文書の 1 行を直す時は**同じ表・リストの全行を実装と突き合わせる**（「同じ壊れ方をする検査は隣に固まっている」の文書版）
- 具体: `guess_view` の `"verified" in q` が「unverified」にも一致していた
  - 抽象: 否定形が肯定形を部分文字列に含む語彙（un-/非/未）は**否定形を先に判定**する

**プロセス上の改善点**:
- ゲートをスクリプトに固めたことで、`&&` の手連鎖で 3 回起きた「pytest の失敗が隠れる」事故の経路が消えた。ただし**スクリプトの exit を測る側**に同じ罠があった（上記 3 件目）

**リポジトリをまたいで使える知見**:
- 「ハッシュは再計算して比較するまで検知にならない」「exit code の証拠はパイプ無しで取る」を `dev/` へ
