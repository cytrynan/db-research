## アーキテクチャパターン

> **既定は「機能単位の縦割り（Vertical Slice）」**。1機能に必要なコードを1ディレクトリに同居させ、
> AIエージェントが1タスクで読むファイル数を最小化する。層で横に割るのは後述の例外条件のときだけ。

### 機能単位の縦割り（既定）

```
src/features/<機能名>/
├── index.*        ← 唯一の入口。外部から参照してよいのはここだけ
├── handler.*      ← ビジネス判断（この機能の本体）
├── validate.*     ← 検証はこの機能の隣に置く（共有バリデータ層を作らない）
├── types.*
└── <機能名>.test.*

src/shared/        ← 3スライス以上で実際に重複してから初めて作る
```

#### 各スライスの責務
- **責務**: 1つの機能（1ユースケース／1エンドポイント）を、入口から永続化まで完結して持つ
- **許可される操作**: 自スライス内の参照、`shared/` の参照、他スライスの `index.*` の呼び出し
- **禁止される操作**: 他スライスの内部ファイルへの直接参照

#### 縦割りの規律（2つだけ）
1. **`shared/` を投機的に作らない**
   「そのうち共通化するから」で先に作ると、共有層という形で層構造が復活する。
   **同じコードが3スライスで実際に重複してから** `shared/` へ移す。
2. **スライスの外を触る変更は「仕様級の判断」として書き戻す**
   `shared/` の変更・スライスの新設・スライス間の依存追加は、実装者の裁量で黙って行わず
   `.steering/` に書き戻す（レビューの判断基準（oracle）になる）。

### 例外: 層で横に割る場合

次のいずれかに当てはまるなら、縦割りをやめて層分離を選ぶ。**選んだ場合はその理由をここに書く**。

- 共有ビジネスルールが支配的（同じ計算・同じ不変条件が全機能に効く。例: 金融計算・リスク管理）
- 不変条件を中央に集約しないと整合性が壊れる
- 強いドメインモデリングが要求される

```

```
