# 方法論・規範を検証する実験の設計と運用

> **対象**: 開発フロー・体制・規範そのものの妥当性を測る**専用実験**（例: 設計書を厚く書く体制と薄い体制のA/B、委任の境界の測定、疎通コストの測定）。通常の開発・調査タスクには適用しない。
> **なぜ専用のガイドが要るか**: 実験は「**測ること自体が成果物**」であり、通常タスクとは失敗の型が違う。**通常の受入検証は、実験の測定器と分析器を検証しない。** 実測で、測定器・推論・パラメータ解釈の3段階すべてで誤りが出た事例がある（後述）。
> 実験の**結果**は知見置き場へ。ここには**やり方**だけ書く。

---

## 1. 起動前チェックリスト

エージェントを1体でも起動する前にこれを潰す。**チェックリストを作らずに始めない**（司令塔のモデルを問わず、指示漏れは毎回チェックリストの欠如から出ている）。

### 測定について

1. **測定器の校正を最初に1件やる。** 使い捨てエージェント1体を起動し、**ハーネスが報告する値と生ログの実測を突合する**。一致しない指標で本番を回さない。
   - 実例: 完了通知の `subagent_tokens` を無検証で採用し、多セグメント体で合算して**結論の符号が逆になった**。1体分の突合（5分）で防げた。
2. **単位を先に決めて全条件で統一する。** 「コンテキスト長」と「実消費」は別物。**コストを述べるときは実消費で**。コンテキスト長で述べてよいのはコンテキスト長の話だけ。
   - **測る値が「モデル特性」か「環境定数（ハーネス仕様）」かも先に画定する**。環境定数なら記録に「環境依存・失効しうる」と明記する。
3. **親側も測る前提で設計する。** 子だけ見ると、仲介型が**仕事を単価の高い親へ移す**効果が見えない。按分の手続き（時刻窓か、ツール使用による用途同定か）を**全条件で同じにする**。混在させると誤差が出る（実測: 一方を「ターン数×平均単価」で概算し、実測値と69%ずれた）。

### 設計について

4. **零点アームを必ず入れる。** 「処置がゼロ」の条件がないと**成分分解ができない**。
   - 実例: 疎通ゼロ条件を採取していたのに使わず、総コスト比を理論値と直接比較して誤結論を出した。零点があれば成分だけ取り出せた。
5. **パラメータ数 < 条件数 にする。** 3未知数なら最低4条件。**3式3未知数は当てはめであって検証ではない**（必ず解けるので反証できない）。
6. **処置差を列挙し「これ以外は同一」を1行ずつ潰す。** 依頼文は**機械diffを取り**、差分行が意図した処置だけかを確認する。
   - 実例1: トポロジだけ変えたつもりが「能動push可 / 受動pull強制」の非対称も混入していた。
   - 実例2: 処置（設計書から構造指定を削除）が**実物に適用されておらず**、比較対象が実質同一コードになった。→ **加工して処置を作ったら、加工後の成果物を意図とdiffで突合してから走らせる。**
   - **処置確認係（常設工程）**: diffとgrepだけでは足りない。**grep語彙は前回の失敗語のコピーにしかならず、別表面のリークを素通しする**。処置を加工で作ったら、実装起動前に**軽量エージェント1体を追加で立てる**:
     - 渡すもの: **加工後の書類だけ**（原本・実験意図・チェック語彙は渡さない＝ブラインド読解）。読み取り専用。
     - 依頼文: 「この書類で実装者が自分で決めることになる設計判断を**すべて列挙**し、各項目に『書類が決めている／委ねている／暗黙に誘導している』のラベルを付けよ。保存構造・識別子の扱い・出力文言・シグネチャからの推測も含めること」
     - 司令塔は**意図した委任リストと突合**し、「委ねたつもり」の項目が『決めている/誘導している』判定ならリーク→修正して再確認。
7. **実行順を counterbalance するか、親コンテキストをリセットする。** 親コンテキストは対話中に単調増加し**リセットされない**ため、**後発条件ほど親側が構造的に不利**。counterbalance できないなら、**順位に対して保守的な向き**（不利な側が勝っている）かを確認して開示する。
8. **予算はサイズでなく反復に配る。** n=4×1回 より **n=3×2回**。反復がないと「N=1」の弁明を毎回書くことになる。
9. **事前レジストレーション。** **予測値を、結果を見る前にファイルへ書いて凍結する**（`.steering/<日付>-<タスク名>/` に置く）。30秒で済む。
   - 予測は「どちらが高いか」だけでなく**数値**で書く。当たれば法則の検証になり、外れれば設計の欠陥が分かる。
   - 実例（成功）: 事前に固定した予測が実測と −3.91% で一致し、モデルの検証として機能した。**予測を書いたアームだけが検証として働いた。**

### 体制について

10. **被験体は編成規律（基本2〜4体・最大5体）の対象外**と解釈してよい。理由: 被験体は「チーム」ではなく**標本**であり、条件間は疎通ゼロの独立標本だから。ただし**その解釈を1行明記する**（黙って超過しない）。条件**内**の体数は規律の範囲に収める。
11. **評価係を後置で立てる。** 実験では特に、**評価対象に「司令塔の測定器と分析の形」を明示的に含める**（§4）。

## 2. 実行中の運用

- **交絡に気づいたら、限界欄に書くだけで終えず、同じ作業内でアームを1本足して消す。** 開示は除去の代わりにならない。
  - 発動条件を決めておく: **「限界欄に書いた交絡のうち、追加1アームで消せるものは消す」**。
  - 実例: 「この差は構造でなく仲介の下手さでは」という交絡を自覚しながらアームを足さず、評価係に指摘されてから追加した。**結果、その交絡が結論の過半を説明していた。**
- **エージェントへの依頼文の原文を一次ログに残す。** 方法論実験では**依頼文自体が処置の一部**。
- **停止したエージェントは SendMessage で再開**（再spawnより安い）。デッドロック（全員が相手待ち）は実在するので、**静止時間を見て介入する**。介入も実測データとして記録する。

## 3. 分析時のチェックリスト

1. **集約量を成分レベルの理論と直接比べない。** 総コストには処置と無関係な床が含まれる。**必ず成分に分解してから理論と比べる。**
   - 実例: 総コスト比 0.352 を理論値 0.167 と比較し「理論は成立しない」と誤結論。1体あたりで見れば**逆に理論が支持された**。
2. **フィットしたパラメータは、既存の極端な観測点へ外挿して検算する。**
   - 実例: 2成分モデルの第1項を「床」と解釈したが、n=1・作業ゼロへ外挿すると実測の**3倍**を予測した。実体は2つの成分の合計だった。**係数が合うことと、係数の意味が正しいことは別。**
3. **条件内の sd と se を毎回出す。** 差を主張する前に、その差が se より大きいか確認する。**「N=1」の弁明を書くより、条件内分散を出す方が安上がり**（追加コストゼロ、同じ生ログから出る）。
   - 実例: 1体あたりの sd が30%・平均の se が9〜15%ある測定で、係数一致「+0.35%」を精度として提示したのは誤り。**真の検証根拠は、同一構成の2条件が 0.43% 差で再現したこと**だった。
4. **「係数が見えない」ときは、モデルの性質かタスク設計の産物かを区別する。**
   - 実例: 「作業量の係数がゼロ」に見えたのは、**タスクが全員に全データを要求する設計**だったため。モデルの性質ではない。**適用条件は処置でなくタスクの性質から書く。**
5. **結論は「断定してよい／弱める／撤回」に区分して書く。** 弱める場合は**推奨文言まで書く**（曖昧に濁さない）。測定条件（モデル層・体数・タスク性質・実施日・キャッシュ状態）を必ず併記する。

## 4. 評価係の使い方（実験特化）

- **後置起動**（全工程完了後）。並行起動しない。
- **モデルは上位以上**。実験・検証系では最上位に近い層を充てる。
- **SendMessage で継続する**（再spawnしない）。コンテキストが維持され、**指摘の一貫性が保たれ、かつ安い**。実測では3往復で司令塔の誤りを3段階とも摘出できた。
- **依頼文に必ず含めるもの**:
  1. 司令塔のモデルと、そのモデルの**既知の弱み**（再発チェックのため）
  2. **ユーザー指定の制約 vs 司令塔の裁量**の区別（混同されると評価が狂う）
  3. 時系列どおりの正確な経過（**自分のツール呼び出しログと突合してから渡す**）
  4. 環境制約（測定できないもの・並列化できないもの）
  5. **司令塔が実際に開いたファイルの一覧**
  6. **司令塔の結論そのものと、対抗仮説を明示して「攻撃せよ」と書く**
- **★最重要**: 評価対象に「配下の成果物」だけでなく **「司令塔の測定器・推論の形・パラメータ解釈」を明示的に含める**。これを書かないと、評価係は成果物レベルの指摘で止まる。
  - 有効だった書き方: 「**対抗仮説: この差は処置でなく司令塔の下手さでは。もし〜していれば数値はどう変わったか見積もれ**」「**この法則は事後に作った説明（後知恵）ではないか**」「**排除できないなら、結論をどこまで弱めるべきか具体的な文言で示せ**」
- **評価係の報告も鵜呑みにしない。** 実測では、評価係の主張を**司令塔が独立に再集計して一致を確認してから**採用した（追認ではなく検証）。**ただし評価係が正しかったので自説を撤回した** — これが正しい順序。

## 5. 失敗のカタログ（実測）

### ★同型の失敗が3連発した事例

| # | 失敗 | 何を疑わなかったか | 結果 |
|---|---|---|---|
| 1 | 測定器を検証しなかった | **指標** | 結論の符号が逆になった |
| 2 | 集約比を成分理論と比較した | **推論の形** | 「理論は成立しない」と誤結論（実際は成立） |
| 3 | フィット係数を外挿検算しなかった | **パラメータの物理的意味** | 係数の解釈が3倍外れ＋精度の誇張 |

**★共通の型**: 対象が **指標 → 推論 → 解釈** と一段ずつ奥へ移動しているだけで、失敗の型は同一。
**「疑ってから測る」を配下の報告には適用するが、自分の道具には適用しない。**

→ **対策は「自分の道具リスト」を明示的に持つこと**: ①指標の定義 ②推論の形（何と何を比べているか） ③パラメータの意味 ④単位 ⑤条件内分散。**この5つを、配下の報告と同じ厳しさで疑う。**
→ **評価係がいなければ3回とも誤ったまま記録に入っていた。** 方法論を検証する実験では**評価係は必須**。

### その他

- **処置が実物に適用されていなかった**（設計書に削除したはずの情報が3か所残存し、比較対象が実質同一に）。→ §1-6 の処置確認係。
- **新仮説を自分の過去ラウンドのデータで反証しなかった**（評価係が司令塔自身の過去データで反証した）。
- **交絡を開示するだけで安価な除去を打たない癖**は、司令塔のモデルを問わず出る。**モデル固有ではなく司令塔役に共通の落とし穴**として扱う。

> **実験の失敗は「実行」ではなく「自分の道具の無検証」から出る。** 配下は指示どおり動く。壊れるのは司令塔の測定器・推論・解釈。

## 6. 測定器（Claude Code 環境・2026-08-01 実測）

| 測定対象 | 場所 | 注意 |
|---|---|---|
| **子の実消費** | `~/.claude/projects/<session>/subagents/agent-<agentId>.jsonl` の `message.usage` | **これが唯一の正しい子側指標**。fresh / cache_creation / cache_read / output の4成分 |
| **親の実消費** | `~/.claude/projects/<session>.jsonl` の `message.usage` | **`message.id` でユニーク化しないと重複行を二重計上する** |
| 子の停止/走行判定 | タスク出力ファイルの更新時刻とサイズ | 完了すると0バイトになる。**中身は読まない**（全トランスクリプトで親のコンテキストが溢れる） |

**罠**:
- **完了通知の `subagent_tokens` は消費量ではない。** セグメント終了時点の**コンテキスト長のスナップショット**。**多セグメント体で合算すると二重計上**になる。
- **エージェントの疎通量の自己申告は使えない**（実測で送受信が一致せず、同一個体が2つの数字を報告）。
- **司令塔（親）自身のトークン量はリアルタイムには取れない。** 事後に親ログから測る。

**コスト換算**: `weighted = fresh + cache_write×1.25 + cache_read×0.1 + output×5`（公開単価比。上位モデルは中位の5倍として換算）。**サブスク枠の実消費とは一致しない可能性があるが、条件間の順位は重み仮定に依存しない**ことを確認してから使う。

## 7. 予算配分

- 実験の総コストは **被験体より司令塔（親）が大きくなりうる**（実測: 親の消費が子18体の合計を上回った）。**「エージェントを増やすと高い」より「司令塔が長く喋ると高い」**。
- したがって **司令塔の大きな読み込み・集計は子に出す**か、**分析スクリプトで1ツール呼び出しに畳む**。生データを親コンテキストに積むと、以降の全ターンで課金され続ける。
- **反復（N≥2）に予算を配る。** 条件を増やすより同じ条件を2回回す方が、結論の確度は上がる。

## 8. 一次記録

- 一次記録は `.steering/<日付>-<タスク名>/` に置く（実験設計・生データ・誤りの経緯・限界の列挙）。
- **誤りの経緯を消さないことが最も価値が高い。** 訂正した結論は削除せず、「一度こう書いたが、こういう理由で撤回した」と残す。次に同じ実験をする人が同じ罠を踏むかどうかはこの記録で決まる。
- 知見の要約は知見置き場へ。**一次記録と要約を混ぜない。**
