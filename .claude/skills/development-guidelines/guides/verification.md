# 検証ガイド (Verification Guide)

「動いたと思う」を「動いたと証明できる」に変えるための設計指針。
**自分のコードだけでは結果が決まらない機能**（課金・認証・外部API・メール認証を挟むフロー）と、
**無人で走らせる自動化**が対象。

コーディング規約は `implementation.md`、開発プロセスは `process.md`、
エージェント体制での受入検証（3層ゲート）は `orchestration` スキルを参照。

---

## 原則1: 検証は必ず「証跡」を残す（記憶を証拠にしない）

標準出力にだけ結果を出すスクリプトは、**実行者が端末を閉じた瞬間に検証不能**になる。
人間の記憶も、AIの記憶も証拠にならない。

- 実行ごとに `reports/<name>-<ISO8601>.json` を書く。中身は「いつ・どのモードで・何を観測したか」の**時系列**
- **後始末は PASS 時だけにする。** 失敗時こそ現場保存が要る
  - 実例: 一時プロファイルを `finally` で常に削除していたため、**課金記録を追う唯一の手がかり（APIキー）が毎回消えていた**。中断で偶然2つ残っていたから追跡できただけ
- 証跡に外部サービスの識別子が入るなら `.gitignore` に入れる（コミットしない）

## 原則2: ground truth はサービス側に聞く（自分のUIを信じない）

アプリのUI表示は**ローカルにキャッシュされた状態**の反映にすぎない。UIだけ見ていると次の2つが区別できない。

- サービス側でそもそも成立していない（＝相手側／操作手順の問題）
- サービス側は成立しているが自分のアプリに反映されていない（＝**自分のコードのバグ**）

対策: 検証スクリプトは **UIとサービスAPIの両方を並行してポーリング**し、判定を分ける。

```
PASS                  : サービス側 OK ＋ UI 反映 OK
FAIL_UI_NOT_UPDATED   : サービス側 OK ＋ UI 未反映  → 自分のコードのバグ
FAIL_NO_PAYMENT       : サービス側 NG              → 手順・設定・相手側の問題
```

従来はどちらも `TIMEOUT` に潰れていた。対処がまったく違うので、**fail の名前を分けること自体が価値**。

## 原則3: 事後検証ツールを別に用意する

「あの実行、本当に成功していたのか？」を後から単独で答えられるコマンドを用意する（例: `npm run e2e:verify`）。
残存する証跡から識別子を拾ってサービスに照会する形にすると、**過去の実行にも遡れる**。

## 原則4: 資格情報を検証スクリプトに持たせない

- パスワード等が絡む手順は「**人間が入力・AIが検証**」の `--assist` 方式にする
- マジックリンク（ログインリンク・確認メール）を挟むE2Eは、スクリプト単体では完結できない。
  → スクリプトは**所定のファイルにURLが書かれるのを待つ**設計にする（例: `reports/.magic-link`）。
  リンクの取得手段（手で貼る / メールAPI経由 / IMAP）を**スクリプトから分離**でき、資格情報を持たせずに済む

## 原則5: ページ操作は文言でマッチさせない

ボタンのラベルは記号1文字（`→`）だったり、後から変わったりする。
**入力欄を起点に `closest('form')` → フォーム内の submit を押す**ような構造ベースの指定にする。

## 原則6: 数値が「ほぼ一致」の時に誤差で済ませない

前回記録と今回の実測がわずかに違う場合、「誤差の範囲」で片付けると回帰を見逃す。
**旧バージョンをその場で再実行して完全一致を取り、差分の原因が外部要因かコード変更かを実行結果で切り分ける。**

## 原則7: UI を操作できなくても「実コードを実環境で1回は動かす」

Server Action / API ハンドラのような**サーバー専用コード**は、ブラウザ操作なしでは呼びにくい。
ここで「ロジックを再現したスクリプトを書いて確かめた」で済ませると、**実物を1行も通っていない検証**になる。
ブラウザ自動操作が使えない環境でも、次の2段で「実機確認」は成立する。

**(a) 書き込み側 — 一時テストから本物の関数を実DBに対して呼ぶ**

- テストランナーの一時ファイルから**本物の関数を import** し、**認証だけモック**して開発DBに対して実行する。
- モックは境界の最小限に留める（認証・キャッシュ再検証・通知送信）。**DB は実物**を使う。
- 実行の前後で観測したい値を自分で数えて出力し、期待値と突き合わせる（before/after が証跡になる）。
- **確認後にファイルを削除し、リポジトリに残さない。** 常設テストにすると外部DB依存のスイートになり CI が壊れる。
  常設したい場合は統合テストとして別コマンド・別環境に分ける判断を明示的に行う。

**(b) 表示側 — 開発サーバに HTTP でログインしてページを取得し、描画文字列を grep する**

- Cookie ベースのログインを curl で通す（CSRFトークン取得 → 資格情報を POST → cookie jar を再利用）。
- 生成 HTML から**実際に描画された文字列**を確認する。スナップショットや純粋関数のテストは
  「関数が正しい」ことしか言えず、「その関数が画面で使われている」ことを保証しない。

**(c) 破壊的な準備は必ず承認を取る**

- 開発DBのリセットや再投入は、実行前にユーザーへ影響（消えるデータ）を明示して承認を取る。
- ついでに分かること: **検証データの投入手順が素のリセット状態から通るか**。
  通らない場合（前提設定が通常シードに含まれていない等）、その手順は「再現できない手順」なので
  検証と同時に記録・課題化する。

## 原則8: 「緩める方向の変更」には負例を必ず置く

判定・フィルタ・ガードを**緩める**変更（拒否を減らす／対象を広げる／しきい値を下げる）で、
**正例の改善だけを測ると「緩めすぎ」を検出できない**。

- 同じ評価セットに**負例**（緩めた後も従来どおり拒否／対象外のままであるべきケース）を入れる。
- **before/after の両方で負例が維持されること**を PASS 条件に固定する。
  正例が 6/10 → 10/10 に改善しても、負例が 8/8 → 5/8 なら**それは改善ではなく防御の穴**。
- 負例は「正例と紛らわしいが決定的に違う」ものを選ぶ。表層の語彙が似ていて意図が違うケースが最良。
- 効果: 「緩めたが緩めすぎていない」を**目視の印象ではなく数字で**言えるようになる。
  レビューでの「本当に大丈夫か」に1行で答えられる。

## 原則9: 判定が多段なら、直したい段を直接叩く評価を作る

「一次判定 → フォールバック判定」のような多段構成で、**上流だけを見る既存の評価は
下流の不具合に対して原理的に無力**。上流は正しく動いており、評価の数字も一切動かないため、
「評価が PASS だから直っている／壊れていない」が両方とも言えない状態になる。

- **直したい段の関数を直接呼ぶミニ評価**（十数ケースで足りる）を新設し、そこで before/after を測る。
- 既存の全体評価は「**その変更が他段に波及していないこと**」の担保に回す（数字が動かないのが正）。
- 変更前に「この評価はどの段を見ているのか」を明示してから着手する。ここを取り違えると、
  無関係な評価を回して「効果が出ない」と誤診する。

## 原則10: 課金を伴う検証は「無料 → 微課金 → 課金」の3段にし、中断前提で再開手順を書く

- **段階を分け、課金の大半（フル実測）は最後の1回だけ**にする。前段で仕様を固めきれば、
  最終実測は「確認」であって「試行錯誤」ではなくなる。
- **課金フェーズは中断されうる前提**で、タスクリストに**中断マーカーと再開手順をその場で書く**
  （何が済んでいて、再開時にどのコマンドを叩けばよいか）。後日・別セッションでの再開コストが消える。
- 実行前に**見積を提示して承認を取り、上限額も決める**。実測コストはスクリプト側に集計させ、
  見積と並べて記録する（次回の見積精度が上がる）。
- 独立した測定は**並列実行**してよい（別プロセス・別ログ）。所要が半分になり、
  外部APIのレート制限に当たらなければ結果も変わらない。

## 原則11: ゲート条件には「未達だった場合の扱い」と「期待値の前提日」も書く

合否ゲート（「FAIL=0」「一致率◯%以上」）を設計に書くとき、**未達時に何が起きるかまで書いていないと、
実行後に判断が止まる**。

- 未達の場合に **(a) 今回の変更による回帰なのか既知の状態なのかをどう切り分けるか**、
  **(b) 誰が最終判断するか** を設計時に書く。
- **定点観測の期待値ファイルには「いつ時点の前提か」を明記する。** 期待値は、機能追加や
  データ追加のたびに陳腐化する。放置すると「**できるようになったのに MISMATCH に数えられる**」
  項目が積み上がり、一致率が改善しなくなって**指標が実態を映さなくなる**。
- 期待値の棚卸しは、データ・知識を足した作業単位の**その場**で行う（別タスクにすると必ず溜まる）。


## 原則12: 集計のバケット分類に catch-all を作らない

結果を分類して集計するとき、最後を `return { bucket: "成功" }` のような **catch-all にすると、
成功と失敗が同じ袋に入る**。しかも集計値としては整合して見えるので、レビューでも気づけない。

- 実例: 「根拠ありで回答できた」バケットが catch-all だったため、**防御が発動して謝絶した
  ケースが同じバケットに落ちていた**。結果「期待どおりのバケットに入ったか」を見る一致率では
  `22/22` と表示され続け、**実際には3件が謝絶していた**。
- 対策:
  - **catch-all は `unknown` に落とす。** 「分類できなかった」を可視化すれば、分類漏れは
    集計に現れる。成功バケットへ黙って吸収させない。
  - **成否を決める一次情報（`answered` / `exitCode` / `status`）を、分類の分岐条件に必ず入れる。**
    派生値（バケット名）だけで合否を判定しない。
  - 「期待どおりのバケットに入ったか」と「**実際に目的を達成したか**」は**別指標として両方出す**。
    前者は時系列比較のために定義を固定し、後者を実態把握に使う。
- **集計値だけでなく、代表ケースの生の出力を必ず目で見る。** 上の実例は、数字を読み直して
  「なぜ改善しないのか」と回答文を開いたときに初めて見つかった。

## 無人実行の完了判定（自動ループを回す場合）

一人の「できました」でループが終わらないよう、**3条件の AND** にする。

1. **終了宣言の権限を1役に限定する**（例: レビュー役のみ）
2. **リテラルな完了宣言**（`<promise>...</promise>` の完全一致など、曖昧に解釈できない形）
3. **オーケストレータ自身が客観コマンド（テストコマンド）を再実行して合格を確認する**

2 の宣言だけだと捏造・早とちりで抜ける。**3 が最終ゲート**になる。

### 無人実行の環境的な地雷

- **無人セッションには承認者がいない。** ファイル編集を許可するだけでは、コマンド実行が「要承認」で全て止まる。
  → 必要なコマンドを**起動時に前渡しする**（`--allowedTools 'Bash(python:*)'` 等）。親セッションの権限は子に継承されない
- 許可は狭めに与えてよい。賢いモデルは許可範囲内で回避策を見つける
- **子セッションは親の設定（出力スタイル等）を継承する。** 成果物ログに装飾やノイズが混入するので、役割プロンプトで出力形式を固定するか設定を分離する
- 役割プロンプトに「**実行結果は実物のみ。推測で書かない**」と明記すると、実行できなかった時に**捏造せず「実行できなかった」と報告する**（フェイルセーフとして実測で機能した）
