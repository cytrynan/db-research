# プロセスガイド (Process Guide)

## 基本原則

### 1. 具体例を豊富に含める

抽象的なルールだけでなく、具体的なコード例を提示します。

**悪い例**:
```
変数名は分かりやすくすること
```

**良い例**:
```typescript
// ✅ 良い例: 役割が明確
const userAuthentication = new UserAuthenticationService();
const taskRepository = new TaskRepository();

// ❌ 悪い例: 曖昧
const auth = new Service();
const repo = new Repository();
```

### 2. 理由を説明する

「なぜそうするのか」を明確にします。

**例**:
```
## エラーを無視しない

理由: エラーを無視すると、問題の原因究明が困難になります。
予期されるエラーは適切に処理し、予期しないエラーは上位に伝播させて
ログに記録できるようにします。
```

### 3. 測定可能な基準を設定

曖昧な表現を避け、具体的な数値を示します。

**悪い例**:
```
コードカバレッジは高く保つこと
```

**良い例**:
```
コードカバレッジ目標:
- ユニットテスト: 80%以上
- 統合テスト: 60%以上
- E2Eテスト: 主要フロー100%
```

## Git運用ルール

### ブランチ戦略（Git Flow採用）

**Git Flowとは**:
Vincent Driessenが提唱した、機能開発・リリース・ホットフィックスを体系的に管理するブランチモデル。明確な役割分担により、チーム開発での並行作業と安定したリリースを実現します。

**ブランチ構成**:
```
main (本番環境)
└── develop (開発・統合環境)
    ├── feature/* (新機能開発)
    ├── fix/* (バグ修正)
    └── release/* (リリース準備)※必要に応じて
```

**運用ルール**:
- **main**: 本番リリース済みの安定版コードのみを保持。タグでバージョン管理
- **develop**: 次期リリースに向けた最新の開発コードを統合。CIでの自動テスト実施
- **feature/\*、fix/\***: developから分岐し、作業完了後にPRでdevelopへマージ
- **直接コミット禁止**: すべてのブランチでPRレビューを必須とし、コード品質を担保
- **マージ方針**: feature→develop は squash merge、develop→main は merge commit を推奨

**Git Flowのメリット**:
- ブランチの役割が明確で、複数人での並行開発がしやすい
- 本番環境(main)が常にクリーンな状態に保たれる
- 緊急対応時はhotfixブランチで迅速に対応可能（必要に応じて導入）

### 複数ワークツリー並行開発の統合（git worktree を使う場合）

1リポジトリを複数のワークツリーに分けて系列ごとに並行開発する構成では、定期的に統合しないと
「同じ機能を別ブランチで別実装した」状態になり、マージのたびに同じ衝突を解決し直すことになる。

**統合の型**（実測で2回運用・再現性あり）:

1. 全ワークツリーの未コミット変更をゼロにする（`git -C <dir> status --porcelain`）。
2. 統合先のワークツリーで各ブランチを順にマージする。
   **並行作業量が最大のブランチを最初にマージする**（そこが実質の本流。以降のブランチは
   差分が小さくなり、判断が「どちらが上位集合か」に単純化される）。
3. 各ワークツリーで `git merge --ff-only <統合先>`（ff できないなら手順2に漏れがある＝止まって調べる）。
4. 全ブランチを push。
5. **コンフリクト解決の判断を開発ログに残す**。同じ統合を再度行うため、前回の記録が次回の手順書になる。

**同一機能の別実装がぶつかったときの解決**: 片方を選ぶ前に、上位集合かどうかを機械的に確認する。

```bash
# 各ブランチ HEAD の同一ファイルが同じ内容か（blob ハッシュ比較）
for b in main feature/a feature/b; do echo "$b $(git rev-parse $b:<path>)"; done
# 実質同一のコミットか（patch-id が一致するか）
git show <sha> | git patch-id --stable
```

`blob が一致 ＋ 一方が他方の追加変更も含む` と確認できた場合にのみ
`git checkout --ours -- <file>`（統合先を採用）で機械的に解決してよい。
**確認せずに `--ours`／`--theirs` を選ばない**（片方にしかない変更を静かに落とす）。

**リモート追跡の確認**: upstream 未設定のブランチや、`origin/<branch>` が別ブランチの古いコミットを
指しているケースがある。マージ前に `git merge-base --is-ancestor <origin側のsha> <統合先>` で
「リモートに未取り込みの作業が無い」ことを確かめる。保証を取らずに push で上書きしない。

**マージ後に依存の再インストールが必要になる場合**: ワークツリーごとに `node_modules` が独立して
いるため、依存解決の前提（pnpm の `overrides` など）が変わるマージの後は、変更したワークツリー
以外が古いまま取り残される。pnpm では非対話シェルで
`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`（modules ディレクトリ削除の確認が取れず中止）として
現れる。復旧は各ワークツリーで `CI=true pnpm install`（`node_modules` は再生成物・ロックファイルは
不変）。**全ワークツリーで install を回してから** typecheck / lint / build を判断する
（片方だけ通って片方が壊れている状態を見落とさないため）。

### 1つの作業ディレクトリを複数エージェントが同時に触るときの事故

ワークツリーを分けていなくても、**作業セッションを分けていれば並行事故は起きる**。
同じディレクトリで2つの作業が同時に走っていた場合に実際に起きたこと:

**1. `git add <ディレクトリ>` が他方の作業中ファイルを巻き込む。**
`git add docs/` のようなディレクトリ単位の追加で、数分前に別の作業が書いたファイルが
ステージされ、そのままコミットに入る。

- **予防**: `git add <ディレクトリ>` を使わず、**自分が作ったパスを明示列挙**する。
- **検知**: コミット前に `git status --short` の出力を必ず読む
  （`A` 行に身に覚えのないパスが無いか）。
- **復旧**: `git reset --soft HEAD~1` → `git restore --staged <path>` → 再コミット。
  `--soft` はワークツリーを触らないので、相手が編集中のファイルは無傷のまま残る。

**2. 識別子（連番・Phase 番号・ディレクトリ名）が衝突する。**
採番表を「着手時に読む」だけでは足りない（相手も同時に読んでいる）。
衝突したら **振り直しの費用が小さい方を動かす**
— issue・ラベル・コミットなど**外部に出た参照が多い側を残す**。

**3. 相手が書き込み中のディレクトリを rename しない。**
相手のプロセスが書き戻して二重になる。採番表に裁定を記録した上で、
相手の作業に通知して rename は相手にやってもらう。

**4. 後から始める側はワークツリーを切って逃げる（構造的な予防）。**
相手が main の作業ツリーで未コミットの変更を多数持っているときに別の作業を始めるなら、
`git worktree add -b <branch> ../<親>-<ブランチ> main` で自分のツリーを切り、計画書・コード・
依存インストール・環境ファイルのコピーまで**そこで完結させる**。`git status` を汚さないので
上の 1〜3 が起きない。

- 新しいワークツリーでは依存インストールに加えて**生成物（ORM クライアント等）の再生成**が要る。
  型チェックが無関係な既存ファイルで落ちたら、まずこれを疑う。
- **ブラウザプレビュー（dev サーバ起動）はセッション起点のディレクトリで動く**ツールがある。
  作業ディレクトリを移しても元のツリーで起動し、相手のビルド成果物に書く。別ワークツリーで
  画面確認をしたいなら**そのディレクトリで新しいセッションを開く**。同じセッションからは
  本番ビルドとテスト（Server Component は `await Page(props)` で呼び、`redirect` / `notFound` を
  throw するモックで分岐を固定）で代替する。
- ワンショットのスクリプト（DB 照会など）は**ワークツリー内に置いて実行し、終わったら消す**
  （外部の一時ディレクトリに置くと依存が解決できない）。

### コミットメッセージの規約

**Conventional Commitsを推奨**:

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type一覧**:
```
feat: 新機能 (minor version up)
fix: バグ修正 (patch version up)
docs: ドキュメント
style: フォーマット (コードの動作に影響なし)
refactor: リファクタリング
perf: パフォーマンス改善
test: テスト追加・修正
build: ビルドシステム
ci: CI/CD設定
chore: その他 (依存関係更新など)

BREAKING CHANGE: 破壊的変更 (major version up)
```

**良いコミットメッセージの例**:

```
feat(task): 優先度設定機能を追加

ユーザーがタスクに優先度(高/中/低)を設定できるようになりました。

実装内容:
- Taskモデルにpriorityフィールド追加
- CLI に --priority オプション追加
- 優先度によるソート機能実装

破壊的変更:
- Task型の構造が変更されました
- 既存のタスクデータはマイグレーションが必要です

Closes #123
BREAKING CHANGE: Task型にpriority必須フィールド追加
```

#### 決定文脈を footer の trailer に残す（意味のある変更で）

コードの diff からは「**何を選ばなかったか・なぜこの制約を置いたか**」が読めない。将来の改変者が同じ検討を繰り返したり、置いた制約を意図を知らずに外したりするのを防ぐため、**設計判断を伴う変更の commit には footer に trailer を足す**（`Key: value` 形式。Conventional Commits の footer と同じ場所）。

| Trailer | 何を書くか |
|---|---|
| `Constraint:` | この変更が満たすべき制約（外すと壊れる前提） |
| `Rejected:` | 検討して採らなかった代替案｜却下理由 |
| `Directive:` | 将来の改変者への警告（「ここを◯◯に変えると△△が壊れる」） |
| `Confidence:` | この判断の確度（high/medium/low と、低い理由） |
| `Scope-risk:` | この変更が影響しうる範囲・巻き込みリスク |
| `Not-tested:` | 検証できていない条件・環境（未検証を正直に残す） |

**例**:

```
fix(sync): 二重計上を同一キー内でのみ抑止する

Constraint: 複数キーにまたがる場合はファンアウトを保持する（利用側が集計で前提にしている）
Rejected: 全キー横断での重複除去｜実データの按分ルールが未確定のため #47 に切り出し
Directive: ここを「全キー横断」に広げる前に #47 の按分仕様を確定させること
Not-tested: 3キー以上にまたがるレコード（本番データに存在するか未確認）
```

**省略してよいのは trivial な commit だけ**（typo 修正・整形・依存の自動更新など、判断を伴わない変更）。判断を伴わない変更に無理に trailer を足さない。

**効果的なPRテンプレート**:

```markdown

- [ ] 新機能 (feat)
- [ ] バグ修正 (fix)
- [ ] リファクタリング (refactor)

## テスト戦略

### テストピラミッド

```
       /\
      /E2E\       少 (遅い、高コスト)
     /------\
    / 統合   \     中
   /----------\
  / ユニット   \   多 (速い、低コスト)
 /--------------\
```

**目標比率**:
- ユニットテスト: 70%
- 統合テスト: 20%
- E2Eテスト: 10%

### テストの書き方

**Given-When-Then パターン**:

```typescript
describe('TaskService', () => {
  describe('タスク作成', () => {
    it('正常なデータの場合、タスクを作成できる', async () => {
      // Given: 準備
      const service = new TaskService(mockRepository);
      const validData = { title: 'テスト' };

      // When: 実行
      const result = await service.create(validData);

      // Then: 検証
      expect(result.id).toBeDefined();
      expect(result.title).toBe('テスト');
    });

    it('タイトルが空の場合、ValidationErrorをスローする', async () => {
      // Given: 準備
      const service = new TaskService(mockRepository);
      const invalidData = { title: '' };

      // When/Then: 実行と検証
      await expect(
        service.create(invalidData)
      ).rejects.toThrow(ValidationError);
    });
  });
});
```

### カバレッジ目標

**測定可能な目標**:

```json
// jest.config.js
{
  "coverageThreshold": {
    "global": {
      "branches": 80,
      "functions": 80,
      "lines": 80,
      "statements": 80
    },
    "./src/services/": {
      "branches": 90,
      "functions": 90,
      "lines": 90,
      "statements": 90
    }
  }
}
```

**理由**:
- 重要なビジネスロジック(services/)は高いカバレッジを要求
- UI層は低めでも許容
- 100%を目指さない (コストと効果のバランス)

## コードレビュープロセス

### レビューの目的

1. **品質保証**: バグの早期発見
2. **知識共有**: チーム全体でコードベースを理解
3. **学習機会**: ベストプラクティスの共有

### 効果的なレビューのポイント

**レビュアー向け**:

1. **建設的なフィードバック**
```markdown
## ❌ 悪い例
このコードはダメです。

## ✅ 良い例
この実装だと O(n²) の時間計算量になります。
Map を使うと O(n) に改善できます:

```typescript
const taskMap = new Map(tasks.map(t => [t.id, t]));
const result = ids.map(id => taskMap.get(id));
```
```

2. **優先度の明示**
```markdown
[必須] セキュリティ: パスワードがログに出力されています
[推奨] パフォーマンス: ループ内でのDB呼び出しを避けましょう
[提案] 可読性: この関数名をもっと明確にできませんか？
[質問] この処理の意図を教えてください
```

3. **ポジティブなフィードバックも**
```markdown
✨ この実装は分かりやすいですね！
👍 エッジケースがしっかり考慮されています
💡 このパターンは他でも使えそうです
```

**レビュイー向け**:

1. **セルフレビューを実施**
   - PR作成前に自分でコードを見直す
   - 説明が必要な箇所にコメントを追加

2. **小さなPRを心がける**
   - 1PR = 1機能
   - 変更ファイル数: 10ファイル以内を推奨
   - 変更行数: 300行以内を推奨

3. **説明を丁寧に**
   - なぜこの実装にしたか
   - 検討した代替案
   - 特に見てほしいポイント

### レビュー時間の目安

- 小規模PR (100行以下): 15分
- 中規模PR (100-300行): 30分
- 大規模PR (300行以上): 1時間以上

**原則**: 大規模PRは避け、分割する

## 自動化の推進（該当する場合）

### 品質チェックの自動化

**自動化する項目**（採用ツールはプロジェクトの技術スタックに合わせて選ぶ。下表は代表例）:

| 目的 | node-ts | python | go | rust |
|------|---------|--------|----|------|
| Lint | ESLint | ruff | golangci-lint | clippy |
| フォーマット | Prettier | ruff format | gofmt | rustfmt |
| 型 / 静的解析 | tsc --noEmit | mypy | go vet | cargo check |
| テスト | Vitest | pytest | go test | cargo test |
| ビルド | tsc | (不要) | go build | cargo build |

いずれのスタックでも「Lint → フォーマット → 型/静的解析 → テスト（→ ビルド）」をコミット前・PR時に自動実行するのが目標。

**実装方法**:

**1. CI/CD (GitHub Actions)** — 下記は node-ts の例。他スタックは上表のコマンドに置き換える（`/init-extras` が検出スタック用の `ci.yml` を配置する）。
```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test
      - run: npm run build
```

**2. Pre-commit フック** — コミット前にlint/型チェックを走らせる。node-ts では Husky + lint-staged、python では pre-commit、go / rust では lefthook や自作フックを使う。下記は node-ts の例。
```json
// package.json
{
  "scripts": {
    "prepare": "husky",
    "lint": "eslint .",
    "format": "prettier --write .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "build": "tsc"
  },
  "lint-staged": {
    "*.{ts,tsx}": [
      "eslint --fix",
      "prettier --write"
    ]
  }
}
```
```bash
# .husky/pre-commit
npm run lint-staged
npm run typecheck
```

**導入効果**:
- コミット前に自動チェックが走り、不具合コードの混入を防止
- PR作成時に自動でCI実行され、マージ前に品質を担保
- 早期発見により、修正コストを最大80%削減（バグ検出が本番後の場合と比較）

**ツール選定のポイント**:
- 採用ツールは技術スタックに合わせて選ぶ（上表参照）
- ツール間の互換性が高い組み合わせを選び、設定の衝突を避ける
- 開発体験と実行速度のバランスを重視する

## 繰り返し手順（スキル・運用スクリプト）の再発防止

同じ工程で**2回目の同じ失敗**を見たら、トラブルシューティング欄に回避策を追記して終わりにしない。
回避策が「知っている人が思い出したときだけ効く」状態では、次回も同じ場所で止まる
（実測: 既知の回避策が手順書の末尾にあるのに本流の手順が旧経路のままで、物理出力を伴う工程で
2回続けて誤出力した）。

やること3点（同じ作業内で）:

1. **既定経路を正しい経路に差し替える**（Step の手順・スクリプトの既定値そのものを変える）。
2. **誤った経路を機構で塞ぐ**（例: 規格外の入力を検知して処理を拒否し、正しい入口を案内する）。
   文言の注意書きは想起に依存するので、ツール側で止める。
3. **「1件テスト → 目視確認 → 本番」を手順に固定する**。物理出力（印刷・発送・送信）や課金を伴う
   工程では特に。今回の損失が2件で済んだのは、この手順が既にあったから。

判断の型: 「既定はこうなっているはず」を疑い、**実際に効いている既定を測る**（例: 機器側の既定と
利用者個人の既定は別に存在し、`Get-*Configuration` 系は前者しか返さないことがある）。原因を1つ直して
再テストしても「変わっていない」なら、同じ症状を出す**別の原因**を探す（今回は2段目に真因があった）。
