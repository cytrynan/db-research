# 新機能の追加 (計画承認ゲート付き自動実行モード)

**重要:** このワークフローは、**計画（ステアリングファイル）をユーザーが承認した後は**、完了まで自動で実行されるように設計されています。承認ゲート（ステップ4末尾）が全体で唯一の停止点です。それ以外では、思考の途中でユーザーに確認を求めたり、作業を中断したりしないでください。

**引数:** 機能名 (例: `/add-feature ユーザープロフィール編集`)

---

## ステップ1: 準備とコンテキスト設定

1. 現在のタスクコンテキストを確立する:
  - 機能名: `[引数で与えられた機能名]`
  - 日付: `[現在の日付をYYYYMMDD形式で取得]`
  - ステアリングディレクトリパス: `.steering/[日付]-[機能名]/`
2. 上記ステアリングディレクトリを作成する。
3. 以下の3つの空ファイルを作成する:
  - `[ステアリングディレクトリパス]/requirements.md`
  - `[ステアリングディレクトリパス]/design.md`
  - `[ステアリングディレクトリパス]/tasklist.md`

## ステップ2: プロジェクト理解

1. `CLAUDE.md`を読み、プロジェクトの全体像を把握する。
2. `docs/`ディレクトリ内の永続ドキュメントを確認し、関連する設計思想やアーキテクチャを理解する。
3. **機能がUI（画面・コンポーネント）に関わる場合**は、プロジェクトルートの`DESIGN.md`を読み、デザイン方向性とトークンを把握する。`DESIGN.md`が存在しない場合は、**design-tokensスキル**をロードして先に作成する。UI実装は全て`DESIGN.md`に従うこと。

## ステップ3: 既存パターンの調査

1. Grepツールを使用し、機能名に関連するキーワードでソースコード(`src/`)を検索する。
  ```bash
  Grep('[機能に関連するキーワード]', 'src/')
  ```
2. 検索結果を分析し、既存の実装パターン、命名規則、コンポーネントの利用方法を特定する。

## ステップ3.5: 体制の判断 (単独処理 か エージェント編成 か)

1. `Skill('orchestration')`をロードし、**モード1（編成の判断）**に従って、この機能を司令塔（あなた）が単独で実装するか、エージェントを編成するかを決める。

2. 判断は**タスクの種類ではなく「成果物の独立性」**で行う。
  - **単独処理**: 逐次依存が強い / 同一ファイルの編集が中心 / 小規模。以降のステップは全て自分で実行する。
  - **編成**: 独立したモジュールの並行実装、フロント・バック・テストの分担など。**基本2〜4体・最大5体**。編成した場合は、依頼文を `orchestration` スキルの**モード2（委任の設計）**の型（対象の個別列挙 / 報告形式の固定 / 禁止事項 / 制約と裁量の区別 / 停止条件）で書く。

3. どちらを選んだか、選んだ理由を1〜2行で記録しておく（ステップ8で `orchestration.md` に書く）。

## ステップ4: 計画フェーズ (ステアリングファイルの生成 → 承認ゲート)

1. `Skill('steering')`を**計画モード**で実行し、ステップ1で作成した3つのファイル (`requirements.md`, `design.md`, `tasklist.md`) の内容を生成する。

2. **【承認ゲート — 唯一の停止点】** 生成した計画の要点（特に `tasklist.md` のタスク構成、およびステップ3.5で決めた体制）をユーザーに提示し、`AskUserQuestion` で承認を求める。
  - **承認された場合:** 以降は停止せず、ただちにステップ5に進み、実装〜検証を自動で完走する。
  - **修正要望がある場合:** 要望を反映して `requirements.md` / `design.md` / `tasklist.md` を更新し、再度この承認ゲートを実行する。
  - この承認ゲートを通過するまではステップ5に進まないこと。

## ステップ5: 実装ループ (tasklist.mdの完全消化)

**このステップは、`tasklist.md`の全タスクが `[x]` になるまで自動で繰り返されるループ処理です。**
**このステップが正常に完了したら、決して停止せず、ただちにステップ6に進むこと。**

**ループ開始:**

1. タスクリストの読み込み:
  - `[ステアリングディレクトリパス]/tasklist.md`ファイルを読み込む。

2. 進捗の確認:
  - ファイル内に未完了タスク (`[ ]` 未着手 / `[~]` 着手中) が存在するか確認する。
  - **もし未完了タスクが存在しない場合（全て `[x]`）:** この実装ループは完了とみなし、ただちに**ステップ6**へ進む。
  - **もし未完了タスクが存在する場合:** 次の処理（3. タスクの実行）に進む。

3. タスクの実行:
  - `tasklist.md`の**先頭にある未完了タスク**を1つ特定する。
  - `Edit`ツールで該当タスクを `[ ]` → `[~]`（着手中）に更新する（まだ完了ではないので `[x]` は付けない）。
  - そのタスクを完了させるために必要な実装作業を実行する。
  - `Skill('steering')`を**実装モード**で使用する。
  - `Skill('development-guidelines')`のコーディング規約を常に遵守する。

4. タスクリストの更新:
  - 実行したタスクが完了したら、`Edit`ツールを使用して`tasklist.md`を更新し、該当タスクを `[~]` から `[x]`（完了）に変更する。

5. ループ継続:
  - **ステップ5の先頭 (1. タスクリストの読み込み) に戻り、処理を繰り返す。**

---
### ※ 実装ループ内の例外処理ルール ※

実装ループの実行中に以下の状況が発生した場合は、このルールに従って自律的に対処し、ループを継続すること。

- **ルールA: タスクが大きすぎる場合**
  - **対処法:** 現在のタスクをより小さな複数のサブタスクに分割する。`Edit`ツールを使い、元のタスクを削除し、その場所に新しいサブタスク（`[ ]`付き）を挿入する。その後、ループを継続する。

- **ルールB: 技術的理由でタスクが不要になった場合**
  - **条件:** 実装方針の変更、アーキテクチャの変更、依存関係の変更など、明確な技術的理由がある場合にのみ適用。
  - **対処法:** `Edit`ツールを使い、該当タスクを `[x] ~~タスク名~~ (理由: [具体的な技術的理由を簡潔に記述])` の形式で更新する。その後、ループを継続する。

- **❌ 絶対禁止の行為:**
  - 未完了タスクを「後でやる」「別タスクにする」などの理由で意図的にスキップすること。
  - 理由なく未完了タスクを放置してループを終了させること。
  - ユーザーに判断を仰ぐこと。

---

## ステップ6: 実装検証 (サブエージェント起動 — 品質ゲート第2層)

1. `tasklist.md`の全タスクが完了したことを最終確認する。
2. `Task`ツールを使用し、`implementation-validator`サブエージェントを起動して品質を検証する。
  - `subagent_type`: "implementation-validator"
  - `description`: "Implementation quality validation"
  - `prompt`: "今回実装した `[機能名]` に関する全ての変更点の品質を検証してください。対象ファイルは `[実装したファイルのパスリスト]` です。コーディング規約、エラーハンドリング、テスト可能性、既存パターンとの整合性を重点的に確認してください。**品質ゲート（lint / typecheck / test）は実装側の申告を信頼せず、必ず自分で再実行して結果を報告してください。** 指摘は項目ごとに「`file:line` ＋ 失敗シナリオ ＋ 修正方針」の形式で書いてください。"

3. **報告を鵜呑みにしない。** 「〜が存在しない」「〜は使われていない」といった**否定形の指摘は、採用する前に自分で別手段（`Grep` / `ls` 等）で1回確認する**（偽陰性が最も多い事故）。
4. 指摘に対応が必要な場合は修正し、ステップ5のループに戻る。

**このステップが正常に完了したら、決して停止せず、ただちにステップ7に進むこと。**

## ステップ7: 自動テストの実行 (品質ゲート第3層 — 司令塔による再実行)

> ステップ6でレビュー側が再実行した結果と、ここでの実行結果が食い違う場合、**その食い違い自体が異常検知**である。数値が合わない時は「どちらかの環境が違う」で流さず、原因を特定してから先に進む。

1. **技術スタックを検出する。** リポジトリ直下のファイルで判定する:

  | 検出ファイル | スタック |
  |---|---|
  | `package.json` | node-ts |
  | `pyproject.toml` | python |
  | `go.mod` | go |
  | `Cargo.toml` | rust |
  | いずれもなし | none |

2. **検出スタックに応じた検証コマンドを順番に実行**し、全てパスすることを確認する:

  | スタック | 実行コマンド (lint → typecheck/静的解析 → test の順) |
  |---|---|
  | node-ts | `npm run lint` → `npm run typecheck` → `npm test` |
  | python | `uv run ruff check .` → `uv run mypy .` → `uv run pytest` |
  | go | `golangci-lint run` → `go vet ./...` → `go test ./...` |
  | rust | `cargo fmt --check` → `cargo clippy` → `cargo test` |
  | none | 検証コマンドなし（このステップはスキップしてステップ8へ） |

  - スクリプト/ツールが未定義でコマンドが存在しない場合は、そのコマンドのみスキップし、残りを実行する。
3. いずれかのコマンドでエラーが発生した場合は、問題を分析し、修正コードを生成・適用してから、再度このステップを実行する。

**このステップが正常に完了したら、決して停止せず、ただちにステップ8に進むこと。**

## ステップ8: 采配の評価 (エージェントを編成した場合のみ)

**ステップ3.5で単独処理を選んだ場合、このステップはスキップしてステップ9へ進む。**

1. `Task`ツールで`orchestrator-reviewer`サブエージェントを起動し、自分の采配を評価させる。
  - `subagent_type`: "orchestrator-reviewer"
  - `description`: "Orchestration review"
  - `prompt`: 以下を必ず含める。
    - **司令塔（あなた）のモデル名**
    - 立てたエージェントとその役割・モデル
    - 各エージェントへの依頼文の要点と、返ってきた報告の要点
    - **司令塔が実際に開いたファイル・実行したコマンドの一覧**
    - どこがユーザー指定の制約で、どこが自分の裁量だったか

2. 指摘は**そのまま受け入れず採否を判断する**。採用しなかった指摘は、その理由も記録する。

**このステップが正常に完了したら、決して停止せず、ただちにステップ9に進むこと。**

## ステップ9: 振り返りとドキュメント更新

1. `Skill('steering')`を**振り返りモード**で実行し、`tasklist.md`に申し送り事項を記載する。
  - 実装完了日（絶対日付）
  - 計画と実績の差分
  - 学んだこと（**具体例と抽象化の両方**を書く）
  - **止まった点・失敗した点を必ず1件**（次の判断を変えるのは成功談より失敗の記録）
  - 次回への改善提案

2. **エージェントを編成した場合**は、`.steering/[日付]-[機能名]/orchestration.md`（ステップ4で未作成なら `.claude/skills/orchestration/templates/orchestration.md` をテンプレに作成）へ、体制・各モデルの実測・受入検証・評価係の指摘・次回への申し送りを記録する。

3. 今回の変更がプロジェクトの基本設計やアーキテクチャに影響を与えるか判断する。影響がある場合、`docs/`内の関連する永続ドキュメントを`Edit`ツールで更新する。

4. **リポジトリをまたいで再利用できる技術知見**（ハマりどころ・回避策・横断的な教訓）が得られていれば、使用者のグローバル知見置き場（例: `~/.claude/dev/`）への追記を提案する。

5. 開発フロー自体の改善点に気づいた場合は、**作業の最後にユーザーへ提案する**（承認なしに `CLAUDE.md` やスキルを書き換えない）。

## 完了条件

このワークフローは、以下の全ての条件を満たした時点で自動的に完了となる。
- ステップ5: `tasklist.md`の全てのタスクが完了状態（`[x]`または正当な理由でスキップ）になっている。
- ステップ6: `implementation-validator`サブエージェントの検証をパスする（品質ゲートは再実行済み）。
- ステップ7: `test`, `lint`, `typecheck`の全てのコマンドが**司令塔自身の再実行で**エラーなく成功する。
- ステップ8: （編成した場合）`orchestrator-reviewer`の評価を受領し、採否を判断済み。
- ステップ9: `tasklist.md`に申し送り事項が記載されている（編成した場合は `orchestration.md` も作成済み）。

この完了条件を満たすまで、自律的に思考し、問題解決を行い、作業を継続すること。
