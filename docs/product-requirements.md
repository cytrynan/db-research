# プロダクト要求定義書 (Product Requirements Document)

> 入力: [ideas/20260929-research-direction.md](ideas/20260929-research-direction.md)、決定台帳 [decisions.md](decisions.md)（D-1〜D-10）。
> 本書は**研究プロジェクトの PRD**なので、「プロダクト」＝研究の成果物（動く検索基盤＋測定結果）と読み替える。

## プロダクト概要

### 名称
**db-research** - 質問の型で振り分ける個人記録の検索基盤（PostgreSQL 上の研究）

### プロダクトコンセプト
- **質問を先に仕分ける**: 検索の前に「探し物／数える／時点／全体」の4型に振り分け、型ごとに別の道具で答える。RAG（意味の近さで上位N件を拾う）は①探し物にだけ使う
- **OKF フォルダが正本、DB は派生の索引**: `~/.claude/references/`・`~/.agents/knowledge/` 等の Markdown（YAML フロントマター付き）を正とし、DB はいつでも捨てて作り直せる
- **時間を2本持つ**: 事実が「いつ正しかったか（有効時間）」と「いつ記録したか（記録時間）」を分けて保存し、「去年9月時点ではどうだったか」に答える

### プロダクトビジョン
K がくろこに投げる日常の質問（「◯◯はどこに書いた？」「未確認の記録は何件？」「あの方針はいつ変わった？」「この案件は全体としてどっちに傾いている？」）に、**それぞれ正しい道具で、根拠つきで**答えられる基盤を PostgreSQL 一つの上に作る。成果は「動くもの」だけでなく、**どの型の質問がどの方式で何%正答するかの測定結果**として残す。将来、個人データを含まない部分だけを会社向け（Supabase）に転用できる形を保つ。

### 目的
- RAG 単体では構造的に答えられない質問（数える・時点・全体）を、PostgreSQL の機能（SQL・時間範囲・要約階層）で受け止められることを**実測で示す**
- くろこの実運用（`references/` 検索、OKF 記録の棚卸し）に**そのまま使える**検索基盤を得る
- OKF 準拠記録がどこまで DB 化に耐えるか（有効期間の欠落、書式ゆれ）を明らかにし、記録規約へ還流する

## ターゲットユーザー

### プライマリーペルソナ: K（本人・唯一の利用者）
- 学生（青学）で、くろこ（Claude Code）を個人アシスタントとして日常的に使う。記録は OKF 準拠の Markdown で `references/`（生活）・`knowledge/`（技術・株・税）・`memory/` に蓄積中（合計 150 ファイル超）
- 技術スタック: Windows 11、PowerShell、Docker Desktop、Python、Git。DB の設計・運用は**これから学ぶ**（本リポは学習も兼ねる）
- 現在の課題: 記録が増え、くろこが `INDEX.md` 経由で探しても**取りこぼす・数を間違える・時系列を追えない**。特に「いつ決めたか」「何件あるか」は今の検索では答えられない
- 期待する解決策: 質問を投げれば、型に応じて正しい方法で答え、**根拠（どのファイルのどの行か）**を返す
- 典型的なワークフロー: 朝にくろこへ相談 → `references/` 参照 → 回答 → 新事実を記録。夜に開発・研究。記録の更新は毎日、質問は1日数回〜数十回

### セカンダリー: くろこ（AI エージェント・機械利用者）
- `references/` 参照を INDEX.md の手動ルーティングから、本基盤への問い合わせに置き換える利用者。**API は人でなくエージェントが叩く前提**で設計する

## 成功指標(KPI)

### プライマリーKPI（研究の成否）
- **★検索品質（最優先）**: RAG の答えの質はほぼ検索の質で決まる（K指示 2026-09-29）。①探し物の検索を**方式ごとに測って比べる**ことを研究の中心に置く
  - 比較する軸: 埋め込みのみ／全文検索のみ／ハイブリッド／＋文脈付与／＋並べ直し（リランキング）の5段
  - 指標: recall@5・recall@20・MRR（正解が何位に出たか）。**各段の数値を表で残す**
  - 目標: 最良の方式で recall@5 **≥ 90%**、かつ各段の改善幅が一次資料（Anthropic: 5.7%→1.9%）と矛盾しない方向
- **質問セット20問の分類完了**: K の実際の質問20問を4型に振り分けた表が `docs/` に存在する（2026-10 中）
- **記録形式の比較（OKF 素 vs くろこ拡張）**: 同じ本文を①素の OKF v0.2 フロントマター ②くろこ拡張（`description` 必須・`type` 閉じた語彙・memory の `metadata:` ネスト・`valid` 独自キー）で取り込み、**検索品質と②③の正答率がどちらで高いかを表で示す**。良い方を採用し、差があれば `dev/recording.md` へ還流
- **型別の正答率（fixture で測定）**:
  - ① 探し物: 正解ファイルが上位5件に入る割合（recall@5） **≥ 90%**（テスト質問 ≥ 20問）
  - ② 数える: 件数・集計の**完全一致 100%**（SQL で答えるため、ずれたら設計欠陥）
  - ③ 時点: 「YYYY-MM 時点の事実」を問う質問の正答 **100%**（バイテンポラル表で機械的に答える）
  - ④ 全体: 要約階層から答えた回答を K が5段階評価し**平均 ≥ 4**（主観指標。K が10問採点）
- **再現性**: `docker compose up` → 取り込み → 測定スクリプトが**1コマンドで完走**し、同じ入力で同じ数値が出る（差分ゼロ）

### セカンダリーKPI
- 取り込み時間: 全 OKF ファイル（約150）の再取り込みが **5分以内**
- ①の改善幅: 文脈付与（Contextual Retrieval）あり／なしで recall@5 の差を記録（一次資料の 5.7%→3.7% に相当する改善が自分のデータでも出るか）
- 記録規約への還流: 研究で見つかった OKF 準拠記録の欠陥（有効期間なし・書式ゆれ）を `dev/recording.md` に **1件以上**反映

## 機能要件

### コア機能(MVP)

#### F1. OKF 取り込み（Markdown → PostgreSQL）

**ユーザーストーリー**:
K として、正本の Markdown を壊さずに検索できるようにするために、OKF フォルダを DB へ取り込む機能が欲しい

**受け入れ条件**:
- [ ] 指定フォルダ配下の `.md` を走査し、フロントマター全体を `jsonb`、`type`/`status`/`generated_at`/`verified_at`/`stale_after` を列に展開して保存する
- [ ] **素の OKF v0.2 とくろこ拡張の両方を読める**: 拡張＝`description` 必須・`type` の閉じた語彙・memory の `metadata:` ネスト（`generated`/`verified`/`type` が1段下）・`updated:`・`INDEX.md`（大文字）・独自キー `valid`。どちらの形式で来たかを列に記録し、後で比較できる
- [ ] `verified` は単一マップでもリストでも受ける（OKF §5 の規定）
- [ ] フロントマターの**日付だけ**の値（`2026-09-28`）も datetime として取り込める（実データの51件が該当）
- [ ] 本文を見出し単位のチャンクに分割し、各チャンクに「どのファイルの何の節か」の文脈文を付ける
- [ ] 再実行は**冪等**（同じ入力で行数が増えない。before/after の差分ゼロで検証）
- [ ] 個人データを含むフォルダ（`references/`）は取り込み先が**ローカル DB のみ**であることをコードで強制する（接続先がループバック以外なら拒否）

**優先度**: P0(必須)

#### F2. 質問の型判定（4型への振り分け）

**ユーザーストーリー**:
くろことして、質問ごとに正しい道具を選ぶために、質問文を「探し物／数える／時点／全体」に分類する機能が欲しい

**受け入れ条件**:
- [ ] 20問の質問セットに対し、K が付けた正解ラベルとの一致 **≥ 90%**
- [ ] 判定結果と理由（どの語で判断したか）を返す。判定不能は「探し物」に倒さず**「不明」として返す**
- [ ] 判定器は LLM でもルールでもよいが、**入出力を fixture でテストできる**形（関数1つ）にする

**優先度**: P0(必須)

#### F3. ① 探し物（ハイブリッド検索）

**ユーザーストーリー**:
K として、「◯◯について書いた記録はどれ？」に根拠つきで答えてもらうために、意味検索と語句検索を組み合わせた検索が欲しい

**受け入れ条件**:
- [ ] pgvector（埋め込み）と PostgreSQL 全文検索の両方を走らせ、結果を統合して上位N件を返す
- [ ] 返却にはファイルパス・見出し・チャンク本文・スコアを含む（根拠が辿れる）
- [ ] **検索方式を切り替えられる**（埋め込みのみ／全文のみ／ハイブリッド／＋文脈付与／＋並べ直し）。方式は引数1つで選べ、測定ハーネス（F7）が全方式を一括で回せる
- [ ] recall@5 / recall@20 / MRR を測るスクリプトがあり、方式ごとの表を出力する
- [ ] 日本語の語句検索が動く（分かち書きの方式は architecture で決める。未決 D-未決4）

**優先度**: P0(必須)

#### F4. ② 数える（SQL＋定義の固定）

**ユーザーストーリー**:
K として、「未確認の記録は何件？」「type 別の内訳は？」に**毎回同じ数字**で答えてもらうために、集計の定義を固定した問い合わせが欲しい

**受け入れ条件**:
- [ ] よく使う集計（未確認件数・type 別件数・期限切れ件数・バンドル別件数）を**ビュー**として定義し、名前で呼べる
- [ ] 同じ質問を3回投げて**3回とも同じ数字**（fixture で検証）
- [ ] 検索（F3）では答えず、必ず SQL 経路を通る（F2 の判定で②なら F3 を呼ばない）

**優先度**: P0(必須)

#### F5. ③ 時点（バイテンポラル）

**ユーザーストーリー**:
K として、「去年9月の時点ではどうだった？」「この方針はいつ変わった？」に答えてもらうために、事実の有効期間と記録時刻を持つ表が欲しい

**受け入れ条件**:
- [ ] 事実テーブルが `valid_from` / `valid_to` / `recorded_at` を持ち、古い事実は削除せず `valid_to` を閉じる
- [ ] 「YYYY-MM-DD 時点で有効だった事実」を1クエリで返せる
- [ ] OKF フロントマターの独自キー `valid: { from, to }` を取り込める。無いファイルは `generated.at` を `valid_from` の暫定値にし、**暫定であることを列で区別**する
- [ ] fixture（方針変更を3回含む記録）で、各時点の答えが100%一致

**優先度**: P0(必須)

#### F6. ④ 全体（要約の階層）

**ユーザーストーリー**:
K として、「この案件は全体としてどっちに傾いている？」に、拾えた数枚でなく全体を見た答えをもらうために、事前に積んだ要約の階層が欲しい

**受け入れ条件**:
- [ ] バンドル → ファイル → 節 の3段で要約を保存する表がある
- [ ] 全体質問には上位の要約から答え、**どの要約を根拠にしたか**を返す
- [ ] 要約の生成コスト（トークン数）を記録する

**優先度**: P1(重要)（MVP では①②③を優先。④は方式が力技で、コストが見えてから決める）

#### F7. 測定ハーネス

**ユーザーストーリー**:
K として、研究の結論を数字で示すために、質問セットを流して型別の正答率を出すスクリプトが欲しい

**受け入れ条件**:
- [ ] `uv run <script>` 1コマンドで F2〜F5 の指標を出力する
- [ ] 出力は Markdown 表（`docs/` に貼れる形）と JSON（差分比較用）
- [ ] 同じ入力で2回走らせて数値が一致する

**優先度**: P0(必須)

### CLIインターフェース

```bash
# 取り込み（正本フォルダ → ローカル PostgreSQL）
uv run dbr ingest ~/.agents/knowledge/dev          # 個人データを含まないバンドルから始める
uv run dbr ingest ~/.claude/references             # ローカル接続以外は拒否

# 質問（型判定 → 該当する道具で回答・根拠つき）
uv run dbr ask "Codex の起動で PATH の罠は何だった？"      # → ① 探し物
uv run dbr ask "未確認の記録は何件？"                     # → ② 数える
uv run dbr ask "2026-08 時点で評価係の起動条件は？"        # → ③ 時点
uv run dbr classify "..."                               # 型判定だけ

# 測定
uv run dbr bench --questions docs/questions.md          # 型別の正答率を出力
```

### 将来的な機能(Post-MVP)

#### F8. Attested Computation（数値の定義を1枚に固定）
OKF v0.2 の型を使い、F4 のビュー定義を「公認された計算」として Markdown 側にも持つ。エージェントは値だけ埋め、式は書き換えられない。
**優先度**: P2(できれば)

#### F9. 会社向け転用（Supabase）
個人データを含まないバンドルに限り、同じマイグレーションを Supabase に流して動くことを確認する。
**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- `ask` の応答: ①③④は **3秒以内**、②は **1秒以内**（ローカル Docker・約150ファイル・約3,000チャンク想定）
- 全件再取り込み: **5分以内**

### ユーザビリティ
- くろこ（エージェント）が CLI の出力をそのまま根拠として引用できる（パス・行番号・スコアを構造化して返す）
- K が `docker compose up` と `uv run dbr ...` の2つだけ覚えれば動く

### 信頼性
- 正本（Markdown）は**読み取り専用**。本基盤は Markdown を一切書き換えない
- DB は捨てて作り直せる（`ingest` の再実行で完全復元。冪等テストで保証）
- スキーマ変更は SQL マイグレーションファイルのみ（D-3）

### セキュリティ（データの置き場）
- 個人データ（`references/`）を取り込む DB は**ループバック（localhost）接続のみ**。コードで強制し、テストで故障注入する（外部ホストを渡して拒否されることを確認）
- `private.md` は**取り込み対象外**（走査から除外。存在すれば拒否）
- 埋め込み生成に外部 API を使う場合、`references/` の本文を外部へ送るかどうかは**K の明示承認が要る**（未決。architecture で方式を決めるまでは `knowledge/` のみで研究する）

### スケーラビリティ
- 研究の範囲は 1万チャンクまで。それ以上は対象外（個人記録の規模を超える）

## スコープ外

明示的にスコープ外とする項目:
- 個人データを Supabase 等の外部ホスティングへ置くこと（D-5）
- pgvector や PostgreSQL 本体の改造（自作 C 拡張）
- Web UI。利用者は K とくろこ（CLI／関数呼び出し）のみ
- 他人の情報を含む記録の取り込み
- 正本 Markdown の自動書き換え（規約への還流は人が行う）
