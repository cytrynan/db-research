# 研究の方向づけ（2026-09-29）

## テーマ
「質問の型で振り分ける検索基盤」を PostgreSQL 上に作る。RAG 単体の研究ではない。
出発点は動画「RAGのその先」（海外Yパパラジオ 2026-09-02、二次資料）の4分類:

| 型 | 例 | RAG の限界 | DB での受け皿 |

## データの置き場（K決定）
- **K の個人データは手元の PostgreSQL（Docker）のみ。外部ホスティング（Supabase 含む）には載せない。**
- Supabase は「将来、会社で使えたらいい」程度。研究の制約にしない。機能差が無いときだけ Supabase 対応の選択肢を優先。
- 研究の題材は、個人データを含まない OKF ファイル群（`C:\Users\meer0\.agents\knowledge\`）から始める。

## OKF との関係
- **OKF フォルダが正本、DB はいつでも捨てて作り直せる派生の索引**。
- フロントマター全体は `jsonb` に保存し、よく使うキー（`type` / `status` / `generated.at` / `verified.at` / `stale_after`）だけ列に出す（OKF の寛容さと衝突させない）。
- **有効期間は OKF に無い**（`generated.at` / `verified.at` はどちらも記録時間）。**K決定: 有効期間を別に持たせる設計で進める**。
  - 記録側: 独自キー `valid: { from, to }` をフロントマターに追加（OKF は未知キーを拒否しない）
  - DB 側: 有効時間（`valid_from` / `valid_to`）と記録時間（`recorded_at`）の2本を持つ。新事実が入ったら旧行は消さず `valid_to` を閉じる
- Attested Computation（OKF v0.2）は動画の②「数値の定義を1枚」と同じ発想。未採用だが再検討条件に該当する。
